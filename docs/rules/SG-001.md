# SG-001 — Potential missing authorization check

| | |
|---|---|
| **Name** | `missing-authorization` |
| **Default severity** | warning (info for low-confidence findings) |
| **Confidence** | high / medium / low (per finding) |
| **Tags** | security, authorization, access-control |

## What it detects

An exported contract function (a `pub fn` in a `#[contractimpl]` block, or any function of a
`#[contractimpl]` trait implementation) that performs a **sensitive operation** while neither the
function itself nor any helper it calls performs an **authorization check**.

Sensitive operations, from most to least severe:

| Operation | Example | Confidence |
|---|---|---|
| Contract upgrade | `env.deployer().update_current_contract_wasm(hash)` or `.update_current_contract(ContractExecutable::Wasm(hash))` | high |
| Token transfer *out of* the contract | `token.transfer(&env.current_contract_address(), &to, &amount)` | high |
| Write to a privileged key (admin, owner, operator, minter, …) | `storage().instance().set(&DataKey::Admin, &a)` | high |
| Any other storage write (`set`, `remove`, `update`, `try_update`) in a function taking an `Address` | `storage().persistent().set(&DataKey::Balance(user), &x)` | medium |
| Any other storage write whose comment says it is admin- or owner-only ("Requires admin authorization", "only the owner", …) | Reflector V3's `set_invocation_costs_config` (Code4rena 2025-10, high) | high |
| Any other storage write in a function taking no `Address`, when at least two other exported functions of the same contract type write state, take no `Address` and always authorize | a setter that forgot the admin check its sibling setters perform | medium |
| Any other storage write | `storage().instance().set(&DataKey::Counter, &n)` | low, reported as **info** |

Privileged keys are recognised by the key's own name — the enum variant, struct name or symbol
(`DataKey::Admin`, `symbol_short!("OWNER")`, or a constant such as `const KEY: Symbol =
symbol_short!("ADMIN")` used as `&KEY`) — not by the enum type or the values passed in, so
`GovernorKey::OperationId(id)` is not privileged and `DataKey::Balance(admin)` is not either.

Recognised authorization checks:

* `address.require_auth()` and `address.require_auth_for_args(args)` on any address;
* calls to helpers whose name looks like an authorization helper — starts with `require`, `enforce`,
  `ensure`, `assert`, `check`, `verify` or `only` and contains `auth`, `role`, `owner` or `admin`
  (e.g. `require_admin(&env)`, `ownable::enforce_owner_auth(&e)`). The name is trusted only when the
  helper is defined outside the crate; when the crate defines it, its body must actually authorize,
  so an empty `fn require_admin(e: &Env) {}` does not count;
* access-control attribute macros such as `#[only_owner]`, `#[only_admin]`, `#[only_role(..)]`,
  `#[has_role(..)]` (OpenZeppelin Stellar contracts);
* any function listed in `auth-functions` in `stellar-guard.toml` or passed with `--auth-fn`.

Helpers are followed transitively through the crate (free functions, `Self::f()` / `Type::f()`
calls, and `self.f()` methods).

### Authorization on some paths only

A check inside an `if` without a matching check in the `else`, inside one `match` arm, or inside a
`for` / `while` body, or inside a closure (`xs.iter().for_each(|x| x.require_auth())`, or a closure
that is never called) does not run on every call. When the only authorization is of this kind, an
upgrade, outflow or privileged write is reported with **medium** confidence and the message
"authorizes only on some code paths". A check in every branch (`if … { a.require_auth() } else {
b.require_auth() }`, or every `match` arm that does not `panic!` / `return`) counts as unconditional.
Plain storage writes behind conditional authorization are not reported, except writes that decrease
a value keyed by a parameter (a balance debit), which are.

```rust
pub fn withdraw(env: Env, user: Address, amount: i128, notify: bool) {
    if notify {
        user.require_auth();   // only when `notify` is true
    }
    // ⚠ SG-001 (medium): anyone can call with notify = false
    token_client(&env).transfer(&env.current_contract_address(), &user, &amount);
}
```

Skipped functions: `__constructor` (runs once at deploy), `__check_auth` (custom account
authorization) and initializer-named functions, which are covered by [SG-005](SG-005.md).

### Authorization by the wrong address

For contracts that keep their own balances, authorization must come from the address whose balance
goes down. SG-001 reports, with **medium** confidence, an exported function that

* authorizes only addresses passed in as parameters (`caller.require_auth()`), and
* decreases a stored value (written as `balance - amount`, `checked_sub`, …) keyed by a *different*
  `Address` parameter, directly or through helpers such as `spend_balance(&e, &victim, amount)`.

```rust
pub fn move_balance(env: Env, caller: Address, from: Address, amount: i128) {
    caller.require_auth();
    let balance = read_balance(&env, &from);
    write_balance(&env, &from, balance - amount);   // ⚠ SG-001: only `caller` authorizes
}
```

Not reported: an allowance keyed by both addresses is also decreased (`transfer_from`,
`burn_from`), or some authorization targets a stored admin or an auth helper (admin clawback).
Token transfers through a token client are not affected: the token contract itself requires the
sender's authorization.

### `require_auth_for_args` that signs nothing relevant

`addr.require_auth_for_args(args)` authorizes only the listed arguments. When a function that
writes storage or moves funds signs an argument list containing **none** of its amount
(`i128`/`u128`) or other `Address` parameters, a signature can be replayed with any amount and
recipient. Reported with **medium** confidence. Signing a deliberate subset (each party of an atomic
swap signing its own side) is not reported.

```rust
pub fn withdraw(env: Env, user: Address, to: Address, amount: i128) {
    user.require_auth_for_args(vec![&env]);   // ⚠ SG-001: `to` and `amount` not signed
    token_client(&env).transfer(&env.current_contract_address(), &to, &amount);
}
```

## Why it matters

Exported functions can be invoked by anyone with arbitrary arguments. Without `require_auth`, any
account can, for example, withdraw another user's funds, take over the admin role, or replace the
contract code.

## Example

```rust
#[contractimpl]
impl Vault {
    pub fn withdraw(env: Env, user: Address, amount: i128) {
        // ⚠ SG-001: missing `user.require_auth()`
        token_client(&env).transfer(&env.current_contract_address(), &user, &amount);
    }
}
```

Fixed:

```rust
pub fn withdraw(env: Env, user: Address, amount: i128) {
    user.require_auth();
    token_client(&env).transfer(&env.current_contract_address(), &user, &amount);
}
```

## Known limitations

* **False positives:** intentionally permissionless functions (counters, keeper "poke" hooks,
  public registration that is safe by design). Suppress with
  `// stellar-guard-ignore SG-001 -- <reason>` or list them under `ignore-functions`.
* **False negatives:** the right-address check needs the debit to be visible as a subtraction on a
  key built from an `Address` parameter; balances updated through `Option` arguments, structs
  holding several addresses, or arithmetic in another crate are not followed.
* Calls are resolved by name, narrowed by module path, impl type or trait (`a::f`, `Self::f`,
  `<T as Trait>::f`). Helpers in local dependency crates of the same scan (`path = ".."` or
  `workspace = true` dependencies) are followed; other crates are invisible unless listed in
  `auth-functions` or named like an auth helper. Macro-generated operations are only visible when
  scanning with `--expand-macros` and `cargo-expand` is installed.
